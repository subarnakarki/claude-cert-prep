What you need to know

How questions are written

Every question sets up a system with a symptom and asks for the best, first or most reliable fix. Usually all four options would work to some degree. You score by knowing why three of them are worse.

  1. Find the symptom and the stakes. Is the failure costly (money, identity, compliance) or just quality? High stakes push toward deterministic fixes.
  2. Find the root cause. Most stems describe one: thin tool descriptions, missing context passed to a subagent, vague criteria, a schema that forces a value.
  3. Read the qualifier. "First step" favors the cheapest fix aimed at the root cause. "Most reliable" favors something deterministic. "Best" weighs both.
  4. Eliminate, then choose. Cross out options that rely on prompt wording for a hard rule, add infrastructure before fixing the obvious cause, or depend on self-reported confidence.
  5. On "select 2", pick two complementary fixes, not two versions of the same idea.

Pace yourself at about 2 minutes a question. Flag anything that runs past 3 minutes and come back to it.

Ten principles that answer most questions

These ideas show up across every domain. If you only remember one section, make it this one.

  1. 01
    Hard rules belong in code, not prompts. When a requirement must hold every time (refund limits, identity checks, compliance), use a hook, a prerequisite gate or a schema. Prompt instructions always have a failure rate.
  2. 02
    Fix the root cause with the simplest tool first. Wrong tool picked? Improve the tool descriptions before building routers or classifiers. Inconsistent output? Add examples before adding infrastructure.
  3. 03
    Be specific, not vague. "Be conservative" or "be careful" never wins. Explicit categories of what to report and what to skip, plus 2–4 examples that show the reasoning, do.
  4. 04
    Subagents start with nothing. They don't inherit the coordinator's conversation. Pass everything they need in the prompt, and keep content separate from metadata such as source and page.
  5. 05
    Let structured signals drive control flow. Loop on stop_reason (tool_use means continue, end_turn means stop), not on parsed text or an iteration cap. Return structured errors, not "Operation failed".
  6. 06
    Never hide failure. Keep "couldn't check" separate from "checked, found nothing". Return partial results with the error. Don't abort the whole workflow because one part failed.
  7. 07
    Less is more for tools and context. Give each agent 4–5 tools scoped to its role. Trim tool output to the fields that matter. Put key facts at the start of long inputs.
  8. 08
    Self-reported confidence and sentiment are unreliable. Route on explicit criteria, or on confidence that has been calibrated against labeled data.
  9. 09
    Independent review beats self-review. A fresh session or instance catches what the generating session misses.
  10. 10
    Schemas fix syntax, not truth. JSON schemas guarantee shape, not correctness. Add semantic checks (calculated vs stated totals), nullable fields so the model doesn't invent values, and "other"/"unclear" enum options.

Domain essentials

Domain 1 alone is over a quarter of the exam, and domains 3 and 4 together are another 40%. Weight your study time the same way.

1. Agentic Architecture & Orchestration 27%

  • Agent loop: send → check stop_reason → on tool_use, run the tools, append the results, loop → on end_turn, stop.
  • Hub-and-spoke: the coordinator owns routing, errors and synthesis. Subagents never talk to each other.
  • Spawning: the coordinator's allowedTools must include "Task". Send independent Task calls in one response so they run in parallel.
  • Gaps in a report usually trace back to the coordinator splitting the topic too narrowly.
  • Hooks: PostToolUse normalizes mixed data such as timestamps. Interception hooks block policy violations (e.g. refunds over $500) and route them to a human.
  • Decomposition: use fixed chains for predictable work and dynamic plans for open-ended work.
  • Sessions: --resume continues a named session, and you should tell it which files changed. fork_session branches to compare approaches. Start fresh with a summary when the old results are stale.
  • Human handoff needs a structured summary: customer ID, root cause, amounts, recommended action.

2. Tool Design & MCP Integration 18%

  • Tool description is the main signal for tool choice: input formats, examples, edge cases, how it differs from similar tools.
  • Structured errors: isError, errorCategory (transient / validation / business / permission), isRetryable.
  • tool_choice: auto lets the model decide. any forces some tool call. {"type":"tool","name":"x"} forces tool x.
  • Config scope: .mcp.json is the shared project config (secrets via ${ENV_VAR}). ~/.claude.json is personal.
  • Build vs reuse: use community servers for standard integrations and custom ones for team-specific needs. Expose catalogs as MCP resources.
  • Built-in tools: Grep searches file contents, Glob matches file names. Edit needs a unique anchor; otherwise fall back to Read + Write.

3. Claude Code Configuration & Workflows 20%

  • CLAUDE.md levels: user ~/.claude/CLAUDE.md (not shared), project .claude/CLAUDE.md or the repo root, and directory level. Run /memory to see which files are loaded.
  • Path-scoped rules: .claude/rules/*.md with paths: globs load only for matching files and work across directories.
  • Commands and skills: shared commands live in .claude/commands/, personal ones in ~/.claude/commands/. Skills go in .claude/skills/ with context: fork, allowed-tools and argument-hint. Skills load on demand; CLAUDE.md is always loaded.
  • Plan mode vs direct execution: use plan mode for large, multi-file or architectural changes and direct execution for clear, scoped fixes.
  • CI: run with -p (non-interactive) and --output-format json --json-schema. On re-review, report only new issues, and review in an independent session.
  • Refinement: give 2–3 concrete input/output examples when prose is misread. Use the interview pattern in unfamiliar domains.

4. Prompt Engineering & Structured Output 20%

  • Review criteria: explicit categories beat vague wording. Temporarily disable noisy categories to rebuild trust.
  • Few-shot: 2–4 examples of ambiguous cases, showing the reasoning and the output format.
  • Schemas: make fields nullable when the source may lack them, and add other + a detail field and unclear to enums.
  • Retries include the document, the failed output and the specific errors. They fix format, not missing information.
  • Batch API: 50% cheaper, up to 24 hours, no SLA, no multi-turn tool use, matched by custom_id. Use it for overnight and weekly jobs, never for blocking checks.
  • SLA math: submission window + 24 hours ≤ the SLA.

5. Context Management & Reliability 15%

  • Case facts: keep amounts, dates and promises in a persistent case-facts block outside the summarized history.
  • Lost in the middle: put key findings first and use clear headers.
  • Escalate on: an explicit request for a human (right away), a policy gap, or no progress. A frustrated customer with a simple issue gets the issue resolved first.
  • Ambiguous matches: if several records match, ask for another identifier rather than guessing.
  • Long sessions: use scratchpad files, subagents, phase summaries and /compact. Use a manifest for crash recovery.
  • 97% overall accuracy can hide weak spots. Break it down by document type and field, and sample before cutting human review.
  • Conflicting sources: report both with attribution and dates.

Night-before checklist

  • I can explain why stop_reason drives the loop and what each value means
  • I know when to use a hook instead of a prompt, and which hook does what
  • I know subagents get no history and need "Task" in allowedTools
  • I can name the four MCP error categories and the three tool_choice modes
  • I know where every CLAUDE.md, rules, commands, skills and MCP config file lives, and who it's shared with
  • I know when to use plan mode, -p, and an independent review session
  • I know the four Batch API facts and can do the SLA math
  • I know the three escalation triggers and the two unreliable signals
  • I can list the wrong-answer patterns from memory
  • My score on full practice runs is 85% or higher in every domain
